# 局域网服务端设计（V1）

> 本文是"两台手机互相浏览对方相册"功能的**唯一设计依据**。先定协议与分层，再写代码；实现与本文不一致时，先改本文。
>
> 上一版手写实现（未完成、方向已废弃）保留在 `document/lan-v1.patch`，仅供对照。

## 1. 目的与范围

- 目标：同一局域网内，两台安装了本 App 的设备互相发现、建立信任，并**只读**浏览对方的相册、分组与图片。
- 不在 V1 范围：下载入库、SSE 实时推送、多设备互传、公网访问、HTTPS。
- 服务端只读：没有上传、删除、重命名接口。token 的权限就是"读"。

## 2. 角色与术语

| 术语 | 含义 |
|---|---|
| 服务端（Host） | 开启"共享"的那台设备，在本机跑一个 HTTP 服务并广播 mDNS |
| 客户端（Guest） | 主动发现并访问对方设备的 App |
| 对端 | 相对说法，两台设备互为对端 |
| 共享会话 | 一次"开启共享 → 关闭共享"期间的服务端生命周期，token 在此期间有效 |
| 配对 | 客户端首次获得 token 的过程（主机弹窗确认） |
| 快照 | 服务端对 data 层的一次性只读查询结果，不是持续订阅 |

## 3. 与"普通前端 → 后端"的差异

| 维度 | 普通前后端 | 本方案 |
|---|---|---|
| 地址 | 固定域名，DNS 解析 | **动态 IP + 随机端口**，靠 mDNS 发现 |
| 服务端 | 常驻服务器集群 | **另一台手机的 App**，随开关启停 |
| 信任 | 账号登录 → token | **同网段 + 配对**（主机弹窗确认） |
| 方向 | 客户端单向请求 | **双向对等**，两台都既是服务端又是客户端 |
| 传输安全 | HTTPS + 证书 | 明文 HTTP（局域网），无证书体系 |
| 可用性 | 高可用 | 对方锁屏/杀后台即断，需要前台服务保活 |
| 数据一致性 | 强一致 | 弱一致：打开页面拉一次快照，不追求实时 |
| 服务端职责 | 完整业务 | 只读三件事：列相册、列图片、取图 |

### 4.1 服务端组件职责

| 组件 | 职责 | 不做什么 |
|---|---|---|
| `LanServer` | 引擎生命周期：`embeddedServer(CIO)`、start/stop、解析真实端口、失败抛异常 | 不处理请求、不读数据库 |
| Ktor（框架） | TCP 监听、HTTP 解析、keep-alive、并发调度、`ContentNegotiation`、`PartialContent`、`AutoHeadResponse` | 业务逻辑 |
| `LanRouter` | `routing { }` 路由表；受保护路由统一写在 `authenticated(tokens) { }` 块里，由块上的拦截器一次性校验并注入 `deviceId`；参数解析与校验（如 `sort`/`desc`）、统一错误响应 | 不映射 DTO |
| `LanAuth` | token 签发/校验/撤销、白名单判定、配对状态机（待确认）；校验统一由 `authenticated` 拦截器执行 | 不碰相册数据 |
| `ShareGateway` | 排序参数 → `AlbumQuery`；调用 data 层快照；Entity → DTO；拼相对媒体地址 | 不写数据库 |
| `LanMedia` | `respondFile` + `PartialContent`（`Range`/`Content-Range`）+ `AutoHeadResponse`（`HEAD`） | 不做鉴权（由 Router 前置） |
| `LanAdvertiser` | NSD 注册/注销，TXT 写 `name/ip/port/version/deviceId` | 不处理请求 |

### 4.2 客户端组件职责

| 组件 | 职责 |
|---|---|
| `LanApi` | Retrofit 接口声明（配对、列表带 `sort`/`desc`、图片） |
| `LanApiFactory` | 按 `ip:port` 生成 Retrofit，**共享一个 OkHttpClient** |
| `LanAuthInterceptor` | 有 token 时注入 `token` 头；配对/探测接口跳过 |
| `LanDiscovery` | NSD 浏览 → 串行 resolve → `List<LanDevice>`，过滤本机 |
| `RemoteRepository` | 对 VM 暴露 `suspend`/`Flow`，把 HTTP 错误映射成 `UiText` |

## 5. 数据链路（完整流程）

```
[开启共享]
  RemotePage 开关 → LanShareController.setEnabled(true)
    ├─ 生成 token(32B)
    ├─ LanServer.start()：绑定随机端口，进入 accept 循环
    ├─ LanAdvertiser.register()：_photomanager._tcp + TXT(name,ip,port,version)
    └─ LanShareService 前台服务：保活 + 通知显示 ip:port

[发现]
  Guest 打开发送页 → LanDiscovery.start()
    ├─ 组播锁 acquire
    ├─ NsdManager.discoverServices("_photomanager._tcp")
    ├─ onServiceFound → 入队 → 串行 resolveService
    └─ resolve 得到 host/port；命中本机 IP 则丢弃；产出 LanDevice

[配对]
  Guest 点设备 → RemoteRepository.pair(device)
    ├─ 确认模式：POST /v1/pair {deviceId,name} → 202 {requestId}
    │      └─ Host 弹窗"允许 xxx 访问？" → 用户允许 → token 生成
    └─ Guest 轮询 GET /v1/pair/{requestId}：202 等待中 / 200 已批准 / 403 拒绝 / 409 超时
  token 存 DataStore（key=deviceId）

[浏览]
  GET /v1/albums?sort=<字段>&desc=<true|false>
        → {albums:[...], defaultSortField, defaultSortDescending, sortField, sortDescending}
  GET /v1/groups        → {groups:[...], ungroupedCount}
  GET /v1/albums/{id}/photos → [{id,name,sizeBytes,width,height,format}]
  GET /v1/media/{photoId}    → 二进制流（Range/HEAD）

  排序参数缺省 = 使用宿主当前排序；返回值同时给出宿主默认排序与本次实际排序

[连接生命周期]
  OkHttp ConnectionPool 复用 ip:port 的 TCP 连接（keep-alive）
  服务端按 Content-Length 循环读下一条请求，空闲 15s 关闭
  连接断开/端口变化 → 客户端按 deviceId 重建 baseUrl，token 仍可复用
```

## 6. 传输层设计

### 6.1 协议与框架

- 传输：**HTTP/1.1 over TCP**，`Connection: keep-alive`；JSON 用 `kotlinx.serialization`（服务端）与 Retrofit `Converter`（客户端）。
- 客户端：**OkHttp + Retrofit**。OkHttp 负责连接池/超时/重试/拦截器；Retrofit 只做"接口 → 请求"的翻译。
- 服务端：**Ktor 2.3.13（CIO 引擎）**，路由 + `ContentNegotiation(json)` + `PartialContent`（Range）+ `AutoHeadResponse`（HEAD）。CIO 不依赖 Netty，适合 Android；服务端核心放在独立 JVM 模块 `:lan`，便于用 `testApplication` 做协议单测。

### 6.2 并发模型

- accept 循环：单协程。
- 每连接：一个协程，顺序处理该连接上的多个请求（HTTP/1.1 管线化不做）。
- 并发上限：4 个活动连接，超出直接 `429`；单连接连续请求超过 100 次主动断开（防止长连占死）。
- 超时：读请求头 10s、读请求体 20s、写响应 30s（媒体流按块写，单块间隔 10s）。

### 6.3 媒体响应

- `GET /v1/media/{id}`：`Content-Length` = 文件大小；`Accept-Ranges: bytes`。
- `Range: bytes=a-b` → `206` + `Content-Range: bytes a-b/total`。
- `HEAD` 只写头部，用于客户端探测大小与类型。
- `Content-Type` 由文件名后缀决定（webp/png/jpg/gif/heic/avif），未知用 `application/octet-stream`。

### 6.4 错误模型

统一响应体：

```json
{ "code": "PAIR_REJECTED", "message": "user denied" }
```

`code` 由 `LanErrorCode` 枚举生成，序列化为**同名大写字符串**（`UNAUTHORIZED`、`INVALID_ID`…）；
重命名枚举项等于修改协议，必须同步客户端与本文档（有契约测试拦住无意改名）。
M2 会补充 `PAIR_REJECTED`、`PAIR_TIMEOUT`。

| HTTP | code | 场景 |
|---|---|---|
| 400 | `INVALID_SORT` | `sort`/`desc` 参数不合法（未知字段、非布尔值） |
| 401 | `UNAUTHORIZED` | 缺 token / token 过期或失效 |
| 403 | `PAIR_REJECTED` | 对端拒绝 |
| 404 | `NOT_FOUND` | 相册、图片、路径不存在 |
| 409 | `PAIR_TIMEOUT` | 等待主机确认超过 60 秒 |
| 429 | `TOO_MANY_CONNECTIONS` | 超过并发上限 |
| 500 | `INTERNAL` | 未预期异常（记日志，不回传堆栈） |
| 503 | `SHARING_OFF` | 服务当前未开启 |

## 7. 发现（mDNS / DNS-SD）

1. Host 通过 `NsdManager.registerService` 注册 `_photomanager._tcp`，TXT：`name`（机型）、`ip`（选定的 IPv4）、`port`、`version`、`deviceId`。
2. Guest 通过 `NsdManager.discoverServices` 查询；`onServiceFound` → 队列 → **串行** `resolveService`（NSD 同时只允许一个 resolve）。
3. resolve 结果优先用 TXT 里的 `ip`（避免拿到 IPv6 链路本地地址），端口来自 serviceInfo。
4. 过滤自己：`LanNetwork.localAddresses()` 命中即丢弃。
5. 页面可见期间持有 `WifiManager.MulticastLock`（需 `CHANGE_WIFI_MULTICAST_STATE`），否则部分 ROM 丢组播包。
6. 失效模式：路由器 **AP 隔离** 时设备间完全不通；Host 服务被系统杀掉时 mDNS 记录消失；IP 变化后由 `deviceId` 重新发现。

## 8. 鉴权与设备白名单

### 8.1 信任的三种状态

"每次连接都要经过批准"的准确含义是：**每次配对都要主机批准**；白名单是"提前批准过"的例外，token 有效期内不逐请求询问。

| 状态 | 判定 | 配对行为 |
|---|---|---|
| 陌生设备 | `deviceId` 不在白名单 | `POST /v1/pair` → `202 {requestId}`，主机弹窗 |
| 本次会话已批准 | 弹窗允许但未勾选"记住" | 发 token，仅本次共享有效；重启共享后重新弹窗 |
| 白名单（记住的设备） | `deviceId` 在白名单 | `POST /v1/pair` → **直接 `200 {token}`**，无弹窗 |

> 白名单只认 `deviceId`，它只是标识、不是强凭证。这在本场景可以接受：
> 同网段、只读、可以随时撤销；要伪装得先在同一 Wi-Fi 且知道 UUID。
> 如果将来需要更强身份，再引入非对称密钥（V3）。

### 8.2 配对流程（对端确认，默认）

1. Guest 生成并持久化 `deviceId`（UUID），发起 `POST /v1/pair {deviceId, name}`；
2. Host 若 `deviceId` 在白名单 → 直接 `200 {token}`；
3. 否则创建 pending（60s），弹窗「允许 “设备名” 访问？」+ 复选框「记住此设备」；
4. 允许 → 发 `200 {token}`；勾选"记住"则写入白名单；
5. Guest 轮询 `GET /v1/pair/{requestId}` 拿到同样的结果；
6. 拒绝 → `403 PAIR_REJECTED`；超时 → `409 PAIR_TIMEOUT`。

> 协议**不返回 `expiresAt`**：token 是滑动过期，每次使用都会顺延，
> 返回一个固定时间反而会误导客户端。客户端只需要在收到 401 时重新配对。

### 8.3 token

- **每台设备独立 token**，32 字节随机；明文只发给 Guest，服务端只存在内存；
- 请求头：**`token: <token>`**（自定义头），**不进 URL**（避免日志、Referer、图片缓存键泄露）；
- 有效期：**滑动空闲过期 2 小时**——每次成功请求都会顺延，活跃浏览永不过期；超过 2 小时未使用才失效；
- 所有 token 都**只存在服务端内存**，关闭共享/进程死亡即全部失效（不落盘）；
- 白名单设备过期后**静默重新配对**（无需用户操作）；非白名单设备需要主机重新确认；
- 401 → 自动重新配对一次；403/409 → 提示"对方拒绝了连接"；
- 过期清理是**惰性**的（`resolve` 时判断），并在**签发新 token 时顺带扫描一次**，
  避免长期共享、很多设备配对过之后过期条目一直滞留；
- 配对结果（Issued/Rejected/Expired）保留 **5 分钟**供客户端重复轮询，之后清理。

### 8.4 白名单数据模型

表 `allowed_devices`（Room，随下一次数据库版本迁移创建）：

| 字段 | 说明 |
|---|---|
| `deviceId` | 客户端生成的 UUID，主键 |
| `name` | 展示名，重新配对时更新 |
| `pairedAt` / `lastSeenAt` | 首次批准时间 / 最近访问时间 |
| `autoApprove` | 是否勾选"记住"；false 表示仅本次会话 |

主机「远程连接」页展示已授权设备列表：名称、最近访问、撤销按钮。

### 8.5 撤销

- 主机点撤销 → 删除该行 + 从内存 token 表移除 → 该设备后续请求 `401`；
- Guest 收到 401 → 自动重配对 → 若被拒 → 提示"已被对方移出白名单"；
- 关闭共享：内存 token 全部失效，白名单记录保留（下次开启后免确认）。

### 8.6 安全边界

- `deviceId` 可被同网段的人伪造，白名单属于"便利性信任"而非强身份；
  靠"仅局域网 + 只读 + 随时撤销 + token 空闲过期"兜底；
- 如果需要更强身份：V3 引入非对称密钥（Guest 持私钥，Host 存公钥，配对时做签名挑战）。

### 8.7 鉴权时序

```
Guest                                   Host
  │ POST /v1/pair {deviceId,name}         │
  │──────────────────────────────────────▶│ deviceId 在白名单？
  │                                       │  ├─ 是 → 直接发 token
  │                                       │  └─ 否 → 创建 pending，弹窗
  │ 202 {requestId}                       │
  │◀──────────────────────────────────────│
  │                                       │ 用户点"允许"（可勾选记住）
  │ GET /v1/pair/{requestId}              │
  │──────────────────────────────────────▶│ 生成 token，写入/更新白名单
  │ 200 {token, expiresAt}                │
  │◀──────────────────────────────────────│
  │ GET /v1/albums   (token)          │
  │──────────────────────────────────────▶│ 校验 token → 快照 → JSON
```

## 9. 服务端数据设计

### 9.1 为什么需要独立的快照查询

现有 data API 是**给页面用的响应式视图**：`observeAlbums(query)` 带分组/收藏/搜索条件且返回 `Flow`；`observePhotos` 是持续订阅。服务端需要的是**无视视图的一次性快照**与按 id 的单条读取。两者语义不同，所以新增：

```kotlin
suspend fun shareAlbums(sortField: AlbumSortField, descending: Boolean): List<AlbumEntity>
suspend fun shareAlbumPhotos(albumId: Long): List<PhotoEntity>
suspend fun sharePhoto(photoId: Long): PhotoEntity?
suspend fun shareAlbumCover(albumId: Long): PhotoEntity?
suspend fun shareGroups(): List<GroupWithAlbumCount>
suspend fun shareUngroupedAlbumCount(): Int
```

复用现有 SQL 构建而不是复制一份：

- `AlbumQuery` 增加 `allGroups: Boolean = false`；
- `buildAlbumQuery` 在 `allGroups = true` 时**跳过**分组/收藏/搜索过滤，只保留排序与 `albumPath` 兜底；
- 共享查询即 `AlbumQuery(sortField, descending, allGroups = true)`。

DAO 只放 SQL，`ShareGateway` 依赖 `AlbumData`，**不直接注入 `PhotoDatabase`**。

### 9.2 DTO 与实体分离

Room 实体不出网。`ShareGateway` 负责映射：

| DTO | 字段 | 说明 |
|---|---|---|
| `DeviceInfoDto` | `deviceId,name,version` | 探测接口返回 |
| `LanAlbumDto` | `id,name,photoCount,sizeBytes,groupId,coverUrl,modifiedAt` | `coverUrl` 是相对路径 `/v1/media/{id}` |
| `LanAlbumListDto` | `albums, defaultSortField, defaultSortDescending, sortField, sortDescending` | 列表响应外层对象，携带排序元信息 |
| `LanGroupDto` | `id,name,albumCount` | 收藏视图不共享 |
| `LanGroupListDto` | `groups, ungroupedCount` | 远端抽屉数据 |
| `LanPhotoDto` | `id,name,sizeBytes,width,height,format,mediaUrl` | 不含本地路径 |
| `LanPairRequestDto` | `deviceId,name` | 白名单里没有该设备时返回 202，等主机确认 |
| `LanPairResponseDto` | `token` | 配对成功，不返回有效期（滑动过期） |
| `LanPairPendingDto` | `requestId` | 等待主机确认 |
| `ErrorDto` | `code,message` | 统一错误体 |

约定：

- **不给字段默认值**：JSON 里每个字段都出现，契约稳定；
- 可空字段显式输出 `null`（例如 `groupId`），客户端能区分"缺失"与"为空"；
- 服务端**不暴露** `sortOrder` 等本地排序值，排序只通过参数与响应元信息表达。

### 9.3 服务端排序（V1）

**为什么放在服务端**：排序语义只实现一份（复用 `AlbumSortField.sqlExpression` 与现有查询构建），避免客户端复制一套后出现 NULL 处理、`COLLATE NOCASE`、稳定次序上的漂移；同时与本地"切换排序 → Loading → 重建"的交互一致。

**请求**

```
GET /v1/albums?sort=<field>&desc=<true|false>
```

| 参数 | 取值 | 缺省行为 |
|---|---|---|
| `sort` | `custom`、`name`、`modified`、`photoCount`、`fileSize` | 使用**宿主当前排序**（`AlbumListSettings`） |
| `desc` | `true` / `false`（仅小写） | 使用该字段的 `defaultDescending` |

非法值（未知字段、非布尔值）→ `400 INVALID_SORT`；未鉴权时**先返回 401**，不校验参数。

**字段映射**

| `sort` | 本地枚举 | 排序表达式 | 默认方向 |
|---|---|---|---|
| `custom` | `CUSTOM` | `sortOrder` | 升序 |
| `name` | `NAME` | `name COLLATE NOCASE` | 升序 |
| `modified` | `MODIFIED_AT` | `julianday(modifiedAt)` | 降序 |
| `photoCount` | `PHOTO_COUNT` | `photoCount` | 降序 |
| `fileSize` | `FILE_SIZE` | `totalSizeBytes` | 降序 |

**响应**

```json
{
  "albums": [ { "id": 1, "name": "…", "photoCount": 2, "sizeBytes": 3,
                "groupId": null, "coverUrl": "/v1/media/9", "modifiedAt": "…" } ],
  "defaultSortField": "custom",
  "defaultSortDescending": false,
  "sortField": "name",
  "sortDescending": false
}
```

- `default*` = **宿主当前的排序设置**，用于远端初始化"默认排序"；
- `sort*` = **本次实际应用**的排序（请求带参数则等于参数，否则等于 default）；
- 两者分开返回，避免把用户当前选择误当成宿主默认值；远端"恢复默认"= 重新请求时不带参数。

**排序稳定性**

- `ORDER BY <表达式> <方向>, albumPath ASC`，同值相册按路径兜底，避免两端刷新顺序抖动；
- `modifiedAt` 为 NULL 的相册始终排在最后（沿用本地 `nullOrder` 逻辑）。

**客户端行为**

```
首次进入  → GET /v1/albums（不带参数）
          → 用 defaultSortField/defaultSortDescending 初始化排序控件
切换排序  → GET /v1/albums?sort=<字段>&desc=<方向>，期间列表区 Loading
恢复默认  → GET /v1/albums（不带参数）
分组过滤  → 仍在客户端按 groupId 过滤，filter 保持数组原序
```

**不进入协议的内容**：`sortOrder`、收藏标记、搜索关键字；远端不提供拖拽，`custom` 只表示"按宿主的自定义顺序展示"。

**测试清单**

| 用例 | 期望 |
|---|---|
| 不带参数 | 使用宿主设置；响应 `sort* == default*` |
| `sort=name&desc=true` | 顺序按名称倒序 |
| `sort=unknown` / `desc=maybe` | `400 INVALID_SORT` |
| 无 token + 非法参数 | `401` 优先 |
| 无相册 | `200` + 空数组 + 默认排序元信息 |
| 同值相册 | 按 `albumPath` 稳定排序 |

### 9.4 性能

- 相册列表对每个相册查一次封面（N+1）。V1 可接受（几十个相册，本地 SQLite 毫秒级）；V2 改成一条 `GROUP BY` 聚合 SQL。
- 快照查询跑在 `Dispatchers.IO`；请求处理协程直接 `suspend` 调用。
- 媒体不读入内存：`RandomAccessFile` + 64KB 块写（Ktor `respondFile` + `PartialContent`）。

## 10. 客户端设计

```kotlin
interface LanApi {
    @POST("v1/pair") suspend fun pair(@Body body: LanPairRequestDto): LanPairResponseDto
    @GET("v1/pair/{id}") suspend fun pairStatus(@Path("id") id: String): LanPairResponseDto
    // sort/desc 均可空：不传 = 使用宿主默认排序，响应里同时带回 default* 与 sort*
    @GET("v1/albums") suspend fun albums(
        @Query("sort") sort: String? = null,
        @Query("desc") desc: Boolean? = null
    ): LanAlbumListDto
    @GET("v1/groups") suspend fun groups(): LanGroupListDto
    @GET("v1/albums/{id}/photos") suspend fun photos(@Path("id") id: Long): List<LanPhotoDto>
    @Streaming @GET("v1/media/{id}") suspend fun media(@Path("id") id: Long): ResponseBody
}
```

- **排序状态**：首次请求用响应里的 `defaultSortField/defaultSortDescending` 初始化远端排序控件；用户切换时带参数重新请求，期间列表区 Loading；"恢复默认"= 不带参数请求；
- **动态 baseUrl**：`LanApiFactory.create(host, port)` 每次 `baseUrl("http://$host:$port/")`，但复用同一个 `OkHttpClient`，连接池才有意义；
- **拦截器**：`token` 注入 + 请求日志（debug）；
- **Coil**：`OkHttpNetworkFetcherFactory(callFactory = { okHttpClient })`，图片请求同样带 token，URL 保持干净；
- **错误映射**：`HttpException` → `UiText.Resource(...)`；400 `INVALID_SORT` 属于客户端 bug（参数由枚举生成，理论上不会出现）；408/超时 → "无法连接对方设备"。

## 11. 实时性：为什么 V1 不做 SSE

- `Flow` 是进程内的响应式流，跨设备必须换一种线协议；SSE 是 `text/event-stream` 长连接，服务端持续写 `data: {...}\n\n`；
- 技术上可行：服务端 collect Room Flow → 写 SSE；客户端 `okhttp-sse` → `Flow<Event>`；
- 但代价高：连接保活、心跳、断线重连、锁屏被杀、耗电，而"看对方相册"对一致性要求很低；
- **V1 结论**：进入页面 / 下拉刷新拉快照。V3 再评估，且只推"相册列表、照片数"这类轻量数据，图片仍走普通 GET。

## 12. 安全边界

| 风险 | 现状/对策 |
|---|---|
| 明文传输 | 局域网内只读；不做 HTTPS（证书体系成本高）。敏感内容靠"仅同网段 + 配对 + 可随时关闭" |
| 任意设备配对 | 对端弹窗确认；token 滑动 2 小时过期 |
| token 泄露 | 只放 header、不进 URL/缓存键；关闭共享立即失效 |
| 越权写 | 服务端只有读接口，协议层面无法写 |
| AP 隔离/后台被杀 | 明确提示"对方可能不可达"；服务端为前台服务并常驻通知 |

## 13. 演进路线

| 版本 | 内容 | 验收 |
|---|---|---|
| **V1** | 服务端 keep-alive + 路由 + 鉴权 + **设备白名单**（对端确认、记住设备、撤销）+ **服务端排序**；客户端 OkHttp/Retrofit；token 进 header；相册/分组/图片只读浏览 | 陌生设备需确认；白名单免确认；撤销后 401；排序默认与宿主一致、可切换；URL 无 token；连接复用可见 |
| V2 | N+1 优化、下载入库（Range 断点续传）、多设备并发调优 | 下载可续传；3 台设备同时访问不互相阻塞 |
| V3 | SSE 推送（可选）、多设备管理、TLS（如需公网） | 对端增删相册自动刷新 |

## 14. 验收清单（V1）

- [ ] 两台设备同一 Wi-Fi 下互相发现，列表 5 秒内出现对方
- [ ] 未配对请求返回 401；对端拒绝 403；确认超时 409
- [ ] 白名单设备只凭 `deviceId` 免确认（已知取舍，见 8.6 安全边界）
- [ ] 配对成功后，重启 Guest App 不用重新配对
- [ ] 陌生设备首次配对 → 主机弹窗；勾选"记住"后写入白名单
- [ ] 白名单设备再次连接 → 无弹窗直接可用；关闭共享再开启仍免确认
- [ ] 主机撤销设备后 → 该设备旧 token 立即 401，Guest 提示被移出白名单
- [ ] token 闲置 2 小时失效、活跃使用自动续期（`:lan` 单测覆盖）
- [ ] `curl` 抓不到 URL 中的 token；请求头里可见 `token`
- [ ] 相册列表、分组、图片全部只读；无写接口
- [ ] 大图（>100MB）流式返回，不 OOM；`HEAD`/`Range` 正常
- [ ] 关闭共享后所有请求失败并提示；前台服务通知可关闭共享
- [ ] 服务端连接复用：同一 `ip:port` 多次请求只有一条 TCP 连接（`netstat`/日志验证）
- [ ] 远端排序默认等于宿主当前排序；切换字段/升降序后顺序正确；"恢复默认"生效
- [ ] 远端排序非法参数返回 400 `INVALID_SORT`（curl 验证）；未带 token 时仍先返回 401
- [ ] 远端不提供拖拽；`custom` 排序只展示宿主的自定义顺序
