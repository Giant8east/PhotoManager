## 2. 本阶段目标与边界

**目标（V1）**：两台同网段设备 发现 → 配对（对端确认）→ 白名单记忆 → 浏览对方相册、分组、图片；客户端接回后 `:app` 恢复绿色。

**不做（留到 V2/V3）**：下载入库、SSE 实时推送、HTTPS、公网访问、多用户权限体系。

## 3. 模块与包的划分（本阶段最重要决策）

`pages/lan` 现有代码引用的类型必须继续存在且签名不变，否则就要改 UI/VM（已明确不允许）。因此：

| 模块 | 内容 | 依赖 |
|---|---|---|
| `:lan`（纯 JVM） | `LanServer`、`LanRoutes`、`LanTokenStore`、全部 DTO、`ShareDataSource` 接口、客户端 `LanApi`/`LanClient` | Ktor、Retrofit、OkHttp、kotlinx |
| `app`（Android） | `LanShareController`（单例）、`LanShareService`、`LanDiscovery`（NSD）、`AlbumData` 快照实现、Hilt 模块 | `:lan` + Android SDK |

**包名统一为 `com.giant8east.photomanager.lan`**。这样 `pages/lan` 的 import 不改一行即可编译。

## 4. 里程碑

### M0 数据接口与 DTO（纯 JVM，可独立验证）

**目标**：服务端拿到"只读快照"的数据来源，且不依赖 Android。

- `:lan` 新增 `ShareDataSource` 接口：
  ```kotlin
  interface ShareDataSource {
      // 排序由服务端执行：字段 + 升降序由请求参数决定，缺省用宿主设置
      suspend fun albums(sortField: LanSortField, descending: Boolean): LanAlbumListDto
      suspend fun groups(): LanGroupListDto
      suspend fun photos(albumId: Long): List<LanPhotoDto>
      suspend fun mediaFile(photoId: Long): MediaFile?   // 含 path/name/size
  }
  ```
- 新增业务 DTO：`LanAlbumDto`、`LanAlbumListDto`（含 `defaultSort*` 与 `sort*`）、`LanGroupDto`、`LanGroupListDto`、`LanPhotoDto`、`MediaFile`、`LanPairRequestDto`、`LanPairResponseDto`、`LanPairPendingDto`、`LanSortField`（线上枚举）。
- `LanSortField` 负责 `custom|name|modified|photoCount|fileSize` 与本地 `AlbumSortField` 的双向映射。
- 单测：假实现验证 DTO 序列化、排序参数透传、非法值映射。

**验收**：`gradlew :lan:test` 绿；新 DTO 的 JSON 字段与设计文档第 9 节一致。

### M1 业务路由（纯 JVM）

**目标**：四个只读端点可用，`albums` 支持服务端排序，`media` 支持 `HEAD`/`Range`。

- `LanRoutes` 挂载：
  - `GET /v1/albums?sort=&desc=&q=` → 解析并校验参数（缺省用宿主默认；`q` 空白视为缺省）→ `ShareDataSource.albums(...)` → `LanAlbumListDto`
  - `GET /v1/groups` → `ShareDataSource.groups()`
  - `GET /v1/albums/{id}/photos` → `ShareDataSource.photos(id)`
  - `GET /v1/media/{id}` → `respondFile`（装 `PartialContent` 插件，自动 206/HEAD）
- 全部走 `requireDevice`；参数非法 → `400 INVALID_SORT`（鉴权优先，未带 token 先 401）；资源不存在 → 404。
- 单测：200/401/404、`Range: bytes=0-3` → 206、`HEAD` 长度正确、`sort` 生效、非法参数 400、缺省等于默认。

**验收**：`gradlew :lan:test` 绿；用 `testApplication` 断言状态码与 `Content-Range`。

### M2 配对与白名单（纯 JVM 先行，Android 持久化后接）

**目标**：对端确认 + 记住设备 + 撤销。

- `POST /v1/pair`：`{deviceId, name}` → 白名单直接 `200 {token}`；否则 `202 {requestId}` 并挂起等待。
- `GET /v1/pair/{requestId}`：轮询结果（`200`/`202`/`409`/`403`）。
- `LanTokenStore` 增加白名单判定接口（先内存，后接 Room）。
- 单测：陌生→202、批准→200、拒绝→403、超时→409、白名单→直接 200、撤销→401。

**验收**：`gradlew :lan:test` 绿；配对状态机覆盖上述 6 条路径。

### M3 Android 承载层

**目标**：服务端在手机上真正跑起来，切后台不断。

- `app/.../lan/LanShareController`（`@Singleton`）：
  - `Mutex` 串行化 start/stop；`state: StateFlow<LanShareState>`；
  - 每次开启新建 `LanServer`，关闭时 stop 并清 token；
  - 向 `ShareDataSource` 注入 `AlbumData` 实现。
- `ShareGateway`（app 侧）：
  - 从 `AlbumListSettings` 读宿主当前排序作为 `defaultSort*`；
  - 把请求参数映射成 `AlbumQuery(sortField, descending, allGroups = true)`；
  - 复用现有 `buildAlbumQuery`，不复制 SQL。
- `app/.../lan/LanShareService`：`startForeground` + 通知（地址/关闭按钮），`onStartCommand` 只做三件快事，耗时进 `serviceScope`。
- mDNS 注册/注销：`_photomanager._tcp` + TXT（name/ip/port/version/deviceId）。
- `ConnectivityManager.NetworkCallback`：网络变化 → 停旧引擎、重建、重注册 mDNS、刷新通知。
- Manifest：清理 `.lan.LanShareService` 死引用，补 `<service foregroundServiceType="dataSync">` 与权限。

**验收**：真机开启共享 → 通知出现 → 浏览器/`curl`（经 `adb forward`）能访问 `/v1/ping`；按 Home 后仍可访问；关闭后端口拒绝连接；`/v1/albums?sort=name` 顺序正确。

### M4 客户端（Retrofit + OkHttp）

**目标**：`pages/lan` 依赖的 API 全部落地。

- `:lan` 新增 `LanApi`（Retrofit 接口）+ `LanApiFactory`（动态 baseUrl，共享 `OkHttpClient`）+ `LanAuthInterceptor`（`token` 头）。
- `LanClient` 包一层，保持 `pages/lan` 需要的签名（`handshake/albums/groups/photos`），并新增：
  ```kotlin
  suspend fun albums(token: String, sort: LanSortField? = null, descending: Boolean? = null): LanAlbumListDto
  ```
- 首次响应写入 `defaultSort*` 供远端初始化；错误映射：`HttpException(401/403/404/409)` → 用户可读提示。
- Coil：`OkHttpNetworkFetcherFactory` 复用同一 client（图片请求自带 token）。

**验收**：`gradlew :app:assembleDebug` **恢复绿色**；单测覆盖 200/401/403、排序参数拼装、URL 不含 token。

### M4.1 客户端缓存（对齐 EhViewer 的 GalleryDetail 策略）

EhViewer 的做法（`EhApplication.mGalleryDetailCache = LruCache<Long, GalleryDetail>(25)`）：
应用级 LRU 按 id 缓存详情，进入页面先查缓存 → 查在途请求 → 都没有才发请求；
缓存随进程存活，超出 25 个按 LRU 淘汰，`onTrimMemory` 或设置项可整体清空。

我们照搬这套结构，缓存对象换成"列表快照"：

| 层 | 我们的实现 | 说明 |
|---|---|---|
| 页面级 | `RemoteAlbumViewModel.state` | 从相册页进详情再返回，VM 仍在，天然不重发 |
| 应用级 | `RemoteAlbumCache`（Hilt `@Singleton`） | `LruCache<AlbumCacheKey, LanAlbumListDto>`，**容量 25** |
| 在途去重 | `RemoteAlbumRepository.inFlight: Map<Key, Deferred<…>>` | 同一 key 共享一个请求，`Mutex` 保护 |
| 请求 | `LanClient.albums(...)` | 仅在前两层都未命中时发起 |

**缓存 key**（漏掉任一项都会串数据）：

```kotlin
data class AlbumCacheKey(
    val deviceId: String,
    val groupId: Long?,      // 未分组 = null
    val sort: LanSortField,
    val desc: Boolean
)
```

**读取顺序**：

```
get(key) 命中 → 直接返回（不显示 Loading）
   ↓ 未命中
inFlight[key] 存在 → await 同一个 Deferred（不重复请求）
   ↓ 不存在
发起请求 → 成功则 put(key, 结果) → 返回；失败不写缓存
```

**并发要点**：

- "检查 + 创建 Deferred + 放入 inFlight" 必须在 `Mutex` 内完成，否则并发时会创建两个请求；
- `async` 跑在应用级 scope（不是调用者的 scope），避免第一个调用者取消连带取消其他等待者；
- `finally` 中移除 `inFlight[key]`，失败后不能卡住后续请求；
- 失败结果不缓存。

**失效策略**：

| 事件 | 动作 |
|---|---|
| 401 / 被主机撤销 | `cache.clearDevice(deviceId)`，提示重新配对 |
| 切换排序 / 分组 | key 不同，天然区分（旧条目由 LRU 淘汰） |
| 下拉刷新 / 重新进入并主动刷新 | 跳过缓存，强制请求并覆盖 |
| 系统低内存（`onTrimMemory`） | `cache.clear()`（Application 实现 `ComponentCallbacks2`） |
| 进程被杀 | 缓存随进程消失（与 EhViewer 一致） |

**TTL 取舍**：EhViewer 没有 TTL，只有容量淘汰；我们同样**不加硬 TTL**，只加一个可选的"软过期（5 分钟）：过期后先渲染旧数据、后台刷新"。V1 先实现"纯 LRU + 手动刷新"，软过期放 V2。

**测试**：

| 用例 | 期望 |
|---|---|
| 连续两次 `albums()` 同 key | 假 client 只被调用 1 次 |
| 并发两次同 key | 只发 1 次请求，两个调用者拿到同一结果 |
| 不同 group/sort | 各发 1 次（key 不同） |
| 请求失败 | 不写缓存，下次仍会重试 |
| 401 后 | `clearDevice` 生效，同 key 再次请求 |
| 超过 25 个 key | 最久未用的被淘汰 |

## 7. Android 承载时序

```
RemotePage 开关
   → LanShareController.setEnabled(true)          [Mutex]
       → new LanServer().start()                  [端口可能抛异常 → 状态置 Error]
       → registerMdns(port, ip)                   [TXT: name/ip/port/version/deviceId]
       → startForegroundService(LanShareService)  [通知：地址 / 关闭]
NetworkCallback.onLost/onAvailable
   → controller.restart()                          [停旧引擎 → 新端口 → 重注册 mDNS → 刷新通知]
通知“关闭” → PendingIntent.getService(ACTION_STOP)
   → Service.onStartCommand → controller.setEnabled(false) → stopSelf()
```

- 无 token 的请求一律 401；撤销后旧 token 立即失效；
- 远端排序：默认等于宿主当前排序、可切换字段与升降序、`custom` 只展示不拖拽；
- 缓存：连续/并发同 key 只请求一次；超过 25 个 key 按 LRU 淘汰；401 后缓存被清；
- 两台真机完成“发现→确认→白名单免确认→浏览→切换排序→撤销”闭环。

## 12. 回退策略

- 每个里程碑单独提交；M0–M2 只动 `:lan` 与测试，出问题可直接回退该提交，不影响 `app`；
- M3 起涉及 Manifest 与 data 层，回退需同时恢复 Manifest 与迁移（迁移一旦发布不删，只加新迁移）；
- `document/lan-v1.patch` 保留旧实现，紧急情况下可 `git apply` 回看或恢复。
